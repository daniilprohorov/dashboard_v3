# ТЗ: настройки дашборда и UART CAN-логгер

Статус: согласовано с пользователем; **реализация не разрешена в рамках текущего задания — только ТЗ для передачи агенту**. Этот документ описывает требуемое поведение, а не существующие возможности прошивки. Для реализации нужно отдельное поручение.

## 1. Назначение и границы

Добавить переход из ячейки `Errors msg` в настройки дашборда, выбор одного из четырёх OBD-II CAN-протоколов и отдельную страницу пассивного CAN-логгера. Логгер передаёт сырые кадры текстовыми строками через CH343 USB–UART. Отдельная CLI для macOS/Linux управляет захватом и сохраняет один событийный CSV. Внешний LLM-агент использует CLI и CSV для исследования; встроенного анализа сигналов нет.

Приоритет требований: для этого среза данный документ определяет объём и поведение. [design.md](design.md) остаётся источником текущего оформления и полей дашборда, [hardware.md](hardware.md) — аппаратных ограничений. [plan.md](plan.md) — более широкий будущий план, не дополнительные критерии этой задачи.

Не входят в этот срез:

- CAN FD, произвольная длина CAN-ID, изменение параметров UART из CLI;
- одновременная работа независимого логгера и OBD-опроса;
- автоматический подбор CAN-протокола или скорости;
- сохранение профиля логгера между перезагрузками;
- запись на SD/во flash платы, поездки, просмотр кадров или графиков на экране;
- фильтры по содержимому payload, встроенное распознавание сигналов и выводы о неисправностях;
- daemon/IPC для управления одним захватом несколькими CLI-процессами;
- Windows, точная синхронизация часов, гарантированно беспотерьная запись любой загрузки CAN.

## 2. Аппаратные ограничения

Плата: Waveshare ESP32-S3-Touch-LCD-7B, ESP-IDF v5.5.5, LVGL 9.

- Один TWAI-контроллер: одна активная скорость и один владелец CAN в каждый момент.
- Classic CAN: стандартный ID 11 бит, расширенный ID 29 бит, payload до 8 байтов. CAN FD не поддерживается контроллером.
- Документированный диапазон скорости CAN: 1 000–1 000 000 бит/с. Не каждое целое значение внутри диапазона достижимо аппаратным делителем.
- CAN использует GPIO19/20 и исключает native USB. EXIO5 остаётся в положении CAN.
- Связь с компьютером — CH343, UART0 GPIO43/44, разъём USB-C с обозначением UART. RS485 не является каналом этого логгера.
- Рабочий канал логгера фиксирован: **2 000 000 бод, 8N1**. Произвольная скорость в команде относится к CAN, не к UART.
- Устройство не может по одному TX определить наличие читателя за CH343. Активность клиента определяется служебным протоколом.
- Аппаратное управление потоком на документированном подключении не предоставлено. Теоретический предел UART 8N1 при 2 Мбод — 200 000 байт/с до накладных расходов текстового протокола. Это не измеренная пропускная способность и не гарантия отсутствия потерь.
- Listen-only не отправляет ни запросов, ни ACK. На стенде передатчику может потребоваться другой активный CAN-узел для подтверждений.

## 3. Экран настроек и профиль дашборда

### 3.1. Навигация

- Касание ячейки `Errors msg` открывает отдельную страницу настроек. Значение ошибок на основном экране сохраняет прежнее назначение; ошибка не является условием доступности перехода.
- Страница настроек содержит выпадающий список протокола, `Apply`, переход в `Logger` и возврат на дашборд.
- Открытие настроек само по себе не приостанавливает OBD-опрос.
- Сохранять существующий монохромный стиль, шрифты и палитру; не перерабатывать основной экран.

### 3.2. Протоколы

| Вариант | Длина ID | Скорость CAN |
|---|---|---|
| ISO 15765-4, 11-bit / 250k | 11 бит | 250 000 бит/с |
| ISO 15765-4, 11-bit / 500k | 11 бит | 500 000 бит/с |
| ISO 15765-4, 29-bit / 250k | 29 бит | 250 000 бит/с |
| ISO 15765-4, 29-bit / 500k | 29 бит | 500 000 бит/с |

29-битный вариант — действующий OBD-II режим с соответствующими адресами запросов и ответов, не только изменение фильтра или подписи в UI.

### 3.3. Применение и сохранение

- Выбор в списке ещё не меняет CAN и сохранённый профиль.
- `Apply` явно применяет и сохраняет выбранный протокол. При успешном применении остановить прежний опрос, безопасно переключить CAN, сбросить старые измерения и поддержку PID, заново обнаружить ECU.
- Отсутствие ответа ECU не отменяет корректно применённый профиль: отображать `No ECU`, не откатывать протокол автоматически.
- Ошибка аппаратного применения должна быть видна; нельзя сообщать об успешном применении неработающей конфигурации.
- После отключения питания восстанавливается только профиль дашборда. Запись логгера автоматически не запускается.
- Не смешивать черновой выбор в UI с действующим/сохранённым профилем.

## 4. Режимы и переходы

| Исходное состояние | Действие / событие | Результат |
|---|---|---|
| Дашборд | Касание `Errors msg` | Настройки; OBD продолжает работу |
| Настройки | Успешный `Apply` | Новый сохранённый профиль, новый цикл обнаружения ECU |
| Настройки | Возврат | Дашборд с действующим профилем |
| Настройки | Кнопка `Logger` | Остановить OBD; открыть логгер, ждать CLI |
| Дашборд / настройки | CLI пытается начать захват | Отказ с указанием необходимости открыть Logger касанием; режим не менять |
| Логгер, ожидание | Корректная команда захвата CLI | Применить явную конфигурацию, начать listen-only захват |
| Логгер, захват | Истекла длительность / Ctrl-C в CLI | Завершить захват; остаться в логгере, ждать новой команды |
| Логгер, захват | 3 секунды без служебных сообщений CLI | Завершить захват с потерей связи; остаться в логгере |
| Логгер, ожидание | Выход на экране | Вернуть дашборд и OBD с сохранённым профилем |
| Логгер, захват | Выход на экране | Немедленно завершить захват с причиной `user_exit`, уведомить CLI при доступной связи, вернуть дашборд и OBD |
| Любое | Перезагрузка | Обычный запуск дашборда; профиль логгера и захват не восстанавливать |

Выход с экрана при записи — **без дополнительного подтверждения**. Данные, уже полученные CLI, сохраняются. Нельзя скрыть логгер и одновременно продолжить его захват после возобновления OBD.

CLI не переводит плату в логгер самостоятельно. Подключение, обнаружение устройства и чтение статуса также не должны менять режим. После ручного входа в логгер агент может выполнять последовательные захваты без повторных касаний.

## 5. Конфигурация логгера

### 5.1. Обязательные параметры запуска

Каждый запуск CLI явно задаёт:

- скорость CAN в бит/с;
- тип принимаемых ID: `11`, `29` или `both`;
- путь выходного CSV.

Длительность опциональна: с длительностью команда заканчивает захват по таймеру, без неё работает до Ctrl-C или внешнего завершения сессии. Профиль дашборда не является неявным источником скорости или формата.

Любая запрошенная скорость принимается только при точной аппаратной достижимости в документированном диапазоне. Недостижимое значение отклоняется с понятной причиной; нельзя молча округлять скорость или частично применять конфигурацию. Вычисленная эффективная скорость отражается в статусе и метаданных.

### 5.2. Фильтр

- Allowlist точных ID и включительных диапазонов ID.
- Элементы списка объединяются через «ИЛИ», затем применяется ограничение по типу ID.
- Пустой allowlist означает все ID выбранного типа, а не отсутствие кадров.
- В режиме `both` числовое условие применяется к ID обоих форматов; тип ID остаётся отдельным признаком кадра.
- Фильтр действует до формирования выходного UART-потока. Отфильтрованные кадры не считаются потерями.
- CLI и экран показывают эффективный фильтр, чтобы агент мог проверить эксперимент.
- Изменять конфигурацию и фильтр между захватами. Live-reconfiguration и несколько управляющих клиентов не требуются.
- Точный синтаксис аргументов и нормализацию диапазонов выбирает реализующий агент и документирует в `--help` и протоколе; семантика выше обязательна.

### 5.3. Пассивность

На всём протяжении захвата CAN находится в listen-only. Не отправлять OBD-запросы, тестовые кадры, ACK и другие передачи от логгера. Профиль логгера не перезаписывает профиль дашборда.

## 6. Экран логгера

Экран — статус и выход, не редактор параметров и не просмотр трафика.

Показывать:

- текущую эффективную скорость CAN и тип ID либо отсутствие применённой конфигурации;
- фильтр в доступном для чтения виде;
- ожидание CLI / активный захват / захват с обнаруженными потерями / завершение или потерю связи;
- получение данных CLI по подтверждениям, отдельно от факта включения UART TX;
- счётчики обнаруженных потерь и причину последнего завершения.

Сырые кадры и payload на экран не выводить. Настройки, старт и остановка записи управляются CLI; единственное действие на экране логгера — выход с оговорённым завершением захвата.

## 7. Текстовый канал UART

### 7.1. Обязательные свойства

- Компактные текстовые строки, не JSONL на проводе и не бинарный поток.
- Явная версия протокола и распознаваемое обрамление строк.
- Различимые команды, ответы, кадры, статусы, счётчики и завершение сессии.
- Идентификация запросов и ответов, чтобы асинхронный CAN-поток не смешивался с результатами команд.
- Обнаружение устройства и его версии, чтение режима/конфигурации, запуск, остановка, подтверждения и heartbeat.
- В рабочем режиме обычный `ESP_LOG` не должен вклиниваться в протокольные строки. CLI должен переживать отдельный непротокольный вывод загрузчика до установления сессии; это не основание скрывать повреждение активного протокольного потока.
- Неподдерживаемая версия, некорректная команда, недостижимая скорость и запуск вне логгера дают явную машинно-различимую ошибку.

Точное кодирование строк и имена команд — решение реализующего агента. До завершения реализации он обязан документировать полный фактический контракт с примерами, единицами измерения и поведением ошибок. Не оставлять документацию с вымышленными командами.

### 7.2. Подтверждения и связь

- CLI периодически подтверждает последний полученный номер кадра и передаёт heartbeat при отсутствии CAN-трафика.
- Сообщение о получении означает получение CLI, не `fsync` и не гарантию сохранения на диске.
- Через **3 секунды** без служебных сообщений CLI плата останавливает захват, показывает потерю связи и ждёт нового явного запуска.
- Не возобновлять старую сессию автоматически при возвращении клиента. Кадры за разрыв не восстанавливаются, повторной передачи не требуется.

### 7.3. Переполнение

- При исчерпании очереди отбрасывать новые кадры, не менять порядок оставшихся и не останавливать захват.
- Нумерация и счётчики должны позволять увидеть обнаруженные пропуски, а не создавать видимость полного лога.
- Отдельно учитывать известные программные отбрасывания и обнаруженные аппаратные переполнения. Для аппаратного события не выдумывать точное количество потерянных кадров, если оно неизвестно.
- Счётчики доступны на экране, в статусе CLI и в событийном CSV.
- Фильтрация не является потерей; полученное CLI подтверждение не доказывает отсутствие потерь до UART или в аппаратном FIFO.

## 8. CLI для внешнего агента

- Поддерживаемые ОС: macOS и Linux. Рекомендуемая реализация — Python 3 с serial-библиотекой; конкретная упаковка остаётся решением агента.
- Предоставить обнаружение портов/устройства, явный выбор порта, статус, описание возможностей и одну команду конфигурации с захватом.
- Один процесс захвата владеет портом до завершения; daemon, IPC и параллельные команды изменения конфигурации не требуются.
- Команда захвата задаёт скорость, тип ID, allowlist, выходной путь и опциональную длительность. По завершении корректно закрывает CSV и освобождает порт.
- Ctrl-C штатно запрашивает остановку и сохраняет полученные данные. Выход с экрана и потеря связи различимы в результате.
- Ответы команд и ошибки доступны в документированном машинно-читаемом виде; согласовать стабильные коды завершения. Человеческая справка и диагностика не загрязняют машинный вывод.
- Не выдавать неподтверждённые настройки, неполную сессию или отсутствие кадров за доказательство отсутствия CAN-трафика.
- CLI не делает выводы о смысле неизвестных байтов. Анализ выполняется внешним агентом.

## 9. Один событийный CSV

Использовать один CSV с заголовком и постоянной схемой колонок. Тип строки определяет заполненные колонки; пустые значения для неприменимых полей допустимы. Не требовать JSON-sidecar или комментариев вне CSV-схемы.

Обязательная информация:

| Событие | Содержимое |
|---|---|
| Начало | Идентификатор сессии, версии устройства/протокола/CLI, время компьютера UTC, исходная временная привязка устройства |
| Конфигурация | Запрошенная и эффективная скорость CAN, тип ID, фильтр, listen-only, параметры UART |
| Кадр | Номер последовательности, время приёма на устройстве в микросекундах, длина ID, ID, RTR, DLC, данные hex |
| Статус / потери | Состояние сессии, подтверждённый номер, известные программные потери, обнаруженные аппаратные переполнения с явной неизвестностью количества кадров при необходимости |
| Завершение | Причина завершения, итоговые счётчики, источник сведений: подтверждение устройства или локальное завершение CLI |

Правила:

- Время кадра — время приёма устройством, не время прихода строки на компьютер. Документировать точку фиксации, начало отсчёта, разрешение и ограничения точности.
- UTC компьютера служит привязкой сессии; точная синхронизация с часами устройства не обещается.
- ID и payload сохраняются без потери ведущих нулей и с документированным основанием счисления. DLC и RTR не выводятся из длины строки payload.
- Последовательность кадров сохраняется; ряды событий не должны изображать дополнительные CAN-кадры.
- При доступной связи завершение содержит финальный статус устройства. Если связи нет, CLI явно отмечает локальное завершение и не подставляет вымышленные финальные счётчики.
- Полученная часть CSV пригодна для чтения после прерывания. После аварийного завершения процесса возможна последняя неполная строка; отсутствие штатного события завершения означает незавершённую сессию.
- Уже полученные данные сохраняются при выходе с экрана. Не обещать сохранение всех буферизованных данных после потери питания или сбоя ОС.

Имена колонок, форматы времени и типизированные значения выбирает агент и фиксирует в документации. Тестовые примеры должны демонстрировать реальный реализованный CSV, не альтернативную схему.

## 10. Точки интеграции существующего кода

На момент согласования:

- `main/main.c`: создание дашборда, запуск demo либо `obd_start`, регистрация touch при наличии GT911.
- `main/dashboard.c`, `main/dashboard.h`: единственный экран; ячейки некликабельны; OBD обновляет сохранённые ссылки на виджеты.
- `main/obd.c`, `main/obd.h`: бесконечный 11-битный OBD-опрос, без API остановки или переключения профиля.
- `components/board/board.c`, `components/board/include/board.h`: аппаратный CAN создаётся через board-слой; дальнейший доступ к пинам в app не добавлять.
- `main/Kconfig.projbuild`, `sdkconfig.defaults`: начальные параметры сейчас compile-time. Все новые Kconfig-решения также в `sdkconfig.defaults`, не в генерируемом `sdkconfig`.
- `partitions.csv`: NVS уже предусмотрена; готового app-хранилища настроек нет.
- `scripts/`, `Makefile`: готового host CLI нет. Прошивка, monitor и CLI делят UART-порт, одновременно владеть им не должны.

Перед реализацией сверить актуальный код. Это карта входа, не предписание сохранить текущую архитектуру.

Обязательные инженерные инварианты:

- Один явный владелец TWAI; безопасная остановка/смена конфигурации перед передачей управления между OBD и логгером.
- Не обновлять удалённые LVGL-виджеты из прежней задачи или demo-таймера после смены экрана. LVGL — только из его задачи либо под `esp_lv_adapter_lock`.
- ISR не блокируется на UART, файловом вводе-выводе или UI; очереди ограничены, потери наблюдаемы.
- Никаких аппаратных обходов board-слоя и конфликтов CAN/native USB.
- Согласовать console/logging с UART-протоколом и высоким baudrate; не ломать штатную прошивку через CH343.
- Не расширять задачу старым планом, автоматическими повторами захвата или скрытыми fallback-режимами.

## 11. Критерии приёмки реализации

Это будущие проверки реализации; при подготовке данного ТЗ они не выполнялись.

| Область | Проверяемое поведение |
|---|---|
| Сборка | `make build` проходит без новых предупреждений |
| Навигация | Errors msg → настройки → Logger; возврат с сохранением назначения основного экрана |
| Протоколы OBD | Каждый из четырёх вариантов работает с соответствующим ECU/симулятором; 29-bit использует правильную адресацию |
| Apply | Выбор без Apply не меняет CAN; Apply сбрасывает старые данные и запускает обнаружение; No ECU не вызывает автоматический откат |
| Сохранение | После перезапуска восстанавливается только сохранённый профиль дашборда, не захват логгера |
| Пассивность | В захвате отсутствуют собственные OBD-запросы и ACK логгера; явно учтена необходимость другого ACK-узла на стенде |
| Вход через экран | CLI не начинает захват вне страницы логгера и не переводит туда устройство |
| Явная конфигурация | Скорость и тип ID обязательны; недостижимая скорость отклоняется без округления и частичного применения |
| Фильтр | Точный ID, обе границы диапазона, объединение диапазонов, пустой список, режимы 11/29/both и исключение неподходящих кадров |
| Содержимое кадров | В CSV правильно различимы одинаковые числовые ID разных форматов, RTR, DLC, ведущие нули, payload и время приёма |
| Завершение | Длительность и Ctrl-C останавливают захват, оставляют страницу логгера; новая запись начинается только новой командой |
| Выход касанием | Во время записи немедленно прекращает захват, CLI сохраняет полученную часть, OBD возобновляется с сохранённым профилем |
| Связь | Тихая CAN-шина не вызывает ложный обрыв при heartbeat; 3 секунды без служебных сообщений завершают захват без автоматического продолжения |
| Потери | Управляемая перегрузка показывает программные потери/аппаратные переполнения отдельно, запись продолжается; фильтрация не считается потерей |
| CSV | Обычный CSV-парсер читает все типы событий; метаданные достаточны без sidecar; штатное и аварийное завершение различимы |
| UART | На реальном CH343 проверена работа 2 Мбод и отсутствие смешивания протокола с console/logging; измерены условия и наблюдаемые потери |
| CLI | На macOS/Linux проверены подключение, конфигурация, захват, завершение и машинные ошибки; непроверенную платформу явно отметить |
| UI | На устройстве проверены касания, читаемость настроек/фильтра и состояния подтверждённой передачи; кадры на экран не выводятся |

Одной сборки или тестов с подменённым serial недостаточно для утверждения о работе CH343, CAN и touch. Если аппаратная проверка недоступна, явно перечислить непроверенные критерии; не называть их выполненными.

## 12. Пакет документации для агента после реализации

Реализующий агент должен обновить текущую UI-документацию, добавить фактическую справку по CLI/протоколу/CSV и сделать инструкции обнаружимыми из команд проекта. Документация должна позволять другому агенту без скрытого контекста:

1. Установить CLI и выбрать именно UART-порт платы, не USB симулятора.
2. Убедиться, что прошивка совместима, прочитать режим и возможности.
3. Попросить человека открыть Logger касанием, если он ещё не открыт.
4. Запустить ограниченный по времени захват с явными скоростью, типом ID и фильтром.
5. Проверить конфигурацию, подтверждения, потери и причину завершения по CSV/результату CLI.
6. Повторить эксперимент с другим фильтром и интерпретировать данные внешним LLM, не принимая отсутствие кадров за доказательство отсутствия сигналов.
7. Вернуть плату в дашборд касанием выхода.

Точные команды, примеры строк и CSV публикуются по фактической реализации. Этот документ фиксирует согласованное поведение и не утверждает, что перечисленные команды или экраны уже существуют.
