## Problem Statement

Водителю нужен доступ к настройкам из дашборда и выбор подходящего OBD-II CAN-протокола без пересборки прошивки. Сейчас дашборд использует только 11-битный OBD-опрос с compile-time скоростью, а ячейка `Errors msg` не поддерживает переход в настройки.

Для исследования неизвестного CAN-трафика пользователю и внешнему LLM-агенту нужен отдельный пассивный захват с явно заданными скоростью, типом ID и фильтром. Сейчас нет режима логгера, host CLI, событийного CSV и управляемой передачи единственного TWAI-контроллера между OBD и логгером. Нельзя исследовать шину, одновременно посылая в неё OBD-запросы, или считать UART TX доказательством получения данных компьютером.

## Solution

Добавить настройки по касанию `Errors msg`: выбор одного из четырёх ISO 15765-4 профилей, явный `Apply`, переход в `Logger` и возврат. Сохраняется только применённый профиль дашборда. Открытие настроек не прерывает OBD; вход в Logger останавливает OBD и передаёт CAN пассивному логгеру.

На отдельной странице Logger показывать эффективную конфигурацию, состояние захвата, подтверждения CLI, обнаруженные потери и причину завершения. Единственное действие на этой странице — выход. Не показывать кадры и не редактировать конфигурацию на экране.

Предоставить CLI для macOS/Linux: обнаружение устройства, статус, возможности и захват с обязательными скоростью CAN, типом ID и выходным путём. CLI получает компактный текстовый поток через CH343 на фиксированных 2 000 000 бод, 8N1, сохраняет один событийный CSV и выдаёт документированные машинно-читаемые результаты. Анализ байтов выполняет внешний агент.

CLI не открывает страницу Logger самостоятельно. После ручного входа разрешены последовательные захваты с разными конфигурациями без повторных касаний. Захват всегда listen-only; после выхода с экрана возобновляется OBD с сохранённым профилем дашборда.

## Implementation Decisions

### Границы и существующее состояние

- Это спецификация для отдельного поручения на реализацию. Подготовка и публикация документа не разрешают менять прошивку или создавать CLI в текущем задании.
- Срез охватывает навигацию, настройки OBD, сохранение профиля дашборда, эксклюзивное владение CAN, пассивный логгер, UART-протокол, host CLI и событийный CSV. Более широкий план развития не добавляет требований.
- Изменяются модули запуска приложения, экранов дашборда/настроек/логгера, OBD-опроса и board CAN. Добавляются хранение профиля, управление захватом, UART-команды и host CLI. Конкретное разбиение внутренних модулей выбирает реализующий агент; отдельный абстрактный framework не требуется.
- Сейчас OBD запускается один раз, не имеет API остановки/смены профиля, использует 11-битные запросы `0x7DF` и ответы `0x7E8–0x7EF`. Существующее сообщение приёма не сохраняет формат ID, RTR и время приёма, а отправка в очередь не учитывает отбрасывания. Нельзя считать этот контракт достаточным для логгера.
- Дашборд хранит ссылки на виджеты; существуют таймер мигания и demo-таймер. Смена экранов не должна оставлять обновления удалённых объектов из OBD или LVGL-таймеров.
- NVS-раздел уже предусмотрен, app-хранилища профиля нет. Готовые host CLI и проектные тестовые сценарии при исследовании не найдены. Перед реализацией сверить актуальное состояние.

### Настройки и профиль дашборда

- Касание `Errors msg` открывает отдельные настройки всегда, не только при ошибке. Назначение значения ошибок сохраняется. Настройки содержат список протоколов, `Apply`, `Logger` и возврат; основной экран не перерабатывается, используются существующие шрифты, монохромный стиль и палитра.
- Открытие настроек не останавливает OBD. Черновой выбор, действующий профиль и сохранённый профиль различаются; изменение списка само по себе не меняет CAN или NVS.
- Доступны ровно четыре OBD-профиля: ISO 15765-4, 11-bit/250k; 11-bit/500k; 29-bit/250k; 29-bit/500k. 29-битный режим использует соответствующие OBD-II адреса запросов и ответов, а не только другую подпись или фильтр.
- Успешный `Apply` безопасно останавливает прежний опрос, применяет и сохраняет профиль, сбрасывает прежние измерения и поддержку PID, начинает новое обнаружение ECU. Аппаратную ошибку показывать; нельзя объявлять неработающую конфигурацию успешно применённой. Ошибку сохранения нельзя выдавать за успешное сохранение.
- Отсутствие ECU после корректного применения означает `No ECU`, не автоматический откат профиля. Возврат без `Apply` использует действующий профиль, а не черновой выбор.
- После перезапуска восстанавливается только сохранённый профиль дашборда. Профиль логгера не сохраняется и не перезаписывает профиль дашборда; запись автоматически не запускается.

### Владение CAN и жизненный цикл

- На плате один TWAI-контроллер: в каждый момент одна активная скорость и один явный владелец. OBD и логгер никогда не работают независимо одновременно. Перед передачей управления безопасно остановить прежнего владельца, callbacks/задачи и конфигурацию.
- Режимы и переходы обязательны:

| Исходное состояние | Действие / событие | Наблюдаемый результат |
|---|---|---|
| Дашборд | Касание `Errors msg` | Настройки; OBD продолжает работу |
| Настройки | Успешный `Apply` | Новый сохранённый профиль и новое обнаружение ECU |
| Настройки | Возврат | Дашборд с действующим профилем |
| Настройки | `Logger` | OBD остановлен; Logger ждёт CLI |
| Дашборд / настройки | CLI запускает захват | Явный отказ с требованием открыть Logger касанием; режим не меняется |
| Logger, ожидание | Корректный запуск CLI | Применена явная конфигурация; начат listen-only захват |
| Logger, захват | Истекла длительность / Ctrl-C | Захват завершён; Logger ждёт новой команды |
| Logger, захват | 3 секунды без служебных сообщений CLI | Захват завершён с потерей связи; Logger остаётся открыт |
| Logger, ожидание | Выход касанием | Дашборд и OBD с сохранённым профилем |
| Logger, захват | Выход касанием | Немедленная остановка с `user_exit`; уведомление CLI при доступной связи; дашборд и OBD с сохранённым профилем |
| Любое | Перезагрузка | Обычный запуск дашборда; профиль логгера и захват не восстанавливаются |

- Выход во время записи не требует подтверждения. Уже полученные CLI данные сохраняются. Нельзя скрыть логгер и продолжить захват после возобновления OBD.
- Подключение CLI, обнаружение, чтение статуса/возможностей не меняют режим. После ручного входа разрешены последовательные захваты; автоматический повтор/продолжение старой сессии запрещён.
- LVGL вызывается только из его задачи или под lock адаптера. ISR не блокируется на UART, UI или файловом вводе-выводе. Очереди ограничены; потери наблюдаемы. Большие буферы размещаются в PSRAM, ISR/DMA-данные — во внутренней RAM согласно правилам проекта.

### Аппаратура и конфигурация логгера

- Цель: Waveshare ESP32-S3-Touch-LCD-7B, ESP-IDF v5.5.5, LVGL 9. Classic CAN: ID 11/29 бит, payload до 8 байтов; CAN FD не поддерживается.
- Доступ к аппаратуре остаётся через board-слой. CAN использует GPIO19/20 и EXIO5 в положении CAN; native USB не включать. Канал компьютера — CH343, UART0 GPIO43/44, USB-C с маркировкой UART, не RS485.
- UART логгера фиксирован: **2 000 000 бод, 8N1**. Скорость в параметрах захвата относится только к CAN. Аппаратное flow control на документированном подключении не предоставлено.
- Каждый запуск требует скорость CAN в бит/с, тип ID `11`/`29`/`both` и путь CSV. Длительность опциональна; без неё захват работает до Ctrl-C или внешнего завершения сессии. Настройки дашборда не служат неявными значениями запуска.
- Принимать скорость только при точной аппаратной достижимости в документированном диапазоне **1 000–1 000 000 бит/с**. Не каждое целое значение достижимо. Недостижимое значение отклоняется с понятной машинно-различимой причиной, без округления и частичного применения. Вычисленная эффективная скорость отражается в статусе и метаданных.
- Allowlist содержит точные ID и включительные диапазоны. Элементы соединяются через «ИЛИ», затем применяется ограничение по типу ID. Пустой список означает все ID выбранного типа. В `both` числовое условие применяется к обоим форматам, а формат сохраняется отдельным признаком.
- Фильтр применяется до формирования UART-потока; исключённые им кадры не являются потерями. CLI и экран показывают эффективный фильтр. Конфигурация меняется только между захватами.
- На всём протяжении захвата listen-only: никаких OBD-запросов, тестовых кадров, ACK или других передач логгера. На стенде передатчику может потребоваться другой активный CAN-узел для ACK; это явно учитывать в инструкции и проверках.
- Все Kconfig-решения задаются в defaults, не в генерируемой конфигурации. Не ломать штатную прошивку платы через CH343; flash, monitor и CLI не должны одновременно владеть UART-портом.

### Экран Logger

- Экран показывает эффективные скорость и тип ID либо отсутствие применённой конфигурации, читаемый фильтр, ожидание CLI, активный захват, обнаруженные потери, завершение/потерю связи, счётчики и причину последнего завершения.
- Подтверждённое получение CLI показывается отдельно от включённого UART TX. По одному TX устройство не определяет наличие читателя за CH343.
- На экране нет сырых кадров, payload, редактора параметров и кнопок старта/остановки. Единственное действие — выход с описанным завершением захвата.

### UART-протокол и потери

- На проводе компактные текстовые строки, не JSONL и не бинарный поток. Нужны явная версия, распознаваемое обрамление, различимые команды, ответы, кадры, статусы, счётчики и завершение сессии.
- Запросы и ответы идентифицируются независимо от асинхронного потока кадров. Протокол поддерживает обнаружение устройства/версии, режим/конфигурацию, возможности, запуск, остановку, подтверждения и heartbeat.
- Неподдерживаемая версия, некорректная команда, недостижимая скорость и старт вне Logger дают явные машинно-различимые ошибки.
- В рабочем режиме обычный `ESP_LOG` не вклинивается в протокольные строки. До установления сессии CLI переносит отдельный загрузочный непротокольный вывод; повреждение активного протокольного потока не скрывается под видом допустимого boot noise.
- CLI периодически подтверждает последний полученный номер кадра и отправляет heartbeat при отсутствии CAN-трафика. Подтверждение означает получение CLI, не `fsync`, не сохранение на диске и не отсутствие потерь до UART.
- Через **3 секунды без служебных сообщений CLI** плата останавливает захват с потерей связи и ждёт нового явного запуска. После возврата клиента старая сессия не возобновляется; повторной передачи и восстановления кадров разрыва нет.
- При исчерпании очереди отбрасываются новые кадры, порядок оставшихся сохраняется, захват продолжается. Нумерация и счётчики делают обнаруженные пропуски видимыми.
- Известные программные отбрасывания учитываются отдельно от обнаруженных аппаратных переполнений. Если аппаратное событие не даёт точного количества потерянных кадров, количество явно неизвестно; нельзя подменять его вымышленным точным числом. Счётчики доступны на экране, в статусе CLI и CSV.
- Теоретический предел UART 8N1 на 2 Мбод — 200 000 байт/с до текстовых накладных расходов. Это не измеренная производительность и не гарантия беспотерьности при любой CAN-нагрузке.

### Host CLI

- Поддерживаются macOS и Linux. Рекомендуется Python 3 с serial-библиотекой; упаковка остаётся решением реализующего агента.
- Предоставить обнаружение портов/устройства, явный выбор порта, статус, возможности и одну команду конфигурации с захватом. Один процесс захвата владеет портом до завершения; daemon, IPC и параллельное управление не нужны.
- Захват принимает явные скорость, тип ID, allowlist, выходной путь и опциональную длительность. Ctrl-C штатно запрашивает остановку; по завершении CLI сохраняет полученные данные, корректно закрывает CSV и освобождает порт. Выход с экрана и потеря связи различаются в результате.
- Документировать машинно-читаемые ответы и ошибки, стабильные exit codes и отделение человеческой справки/диагностики от машинного вывода.
- Не выдавать неподтверждённую конфигурацию, неполную сессию или отсутствие кадров за доказательство отсутствия CAN-трафика. CLI не интерпретирует неизвестные байты и не диагностирует автомобиль.

### Событийный CSV

- Один CSV с заголовком и постоянной схемой колонок. Тип события определяет заполненные поля; неприменимые поля могут быть пустыми. Не требуются JSON-sidecar или комментарии вне CSV-схемы.

| Событие | Обязательное содержимое |
|---|---|
| Начало | ID сессии; версии устройства, протокола и CLI; UTC компьютера; исходная временная привязка устройства |
| Конфигурация | Запрошенная и эффективная скорость CAN; тип ID; фильтр; listen-only; параметры UART |
| Кадр | Номер последовательности; время приёма устройством в микросекундах; длина ID; ID; RTR; DLC; данные hex |
| Статус / потери | Состояние сессии; подтверждённый номер; известные программные потери; обнаруженные аппаратные переполнения с явной неизвестностью количества кадров, если необходимо |
| Завершение | Причина; итоговые счётчики при наличии; источник сведений — подтверждение устройства или локальное завершение CLI |

- Время кадра — время приёма устройством, не прихода строки на компьютер. Документировать точку фиксации, начало отсчёта, разрешение и ограничения точности. UTC компьютера — привязка сессии, не обещание точной синхронизации.
- ID и payload сохраняются с ведущими нулями и документированным основанием счисления. RTR и DLC — самостоятельные признаки, не производные от длины payload-строки. Одинаковые числовые ID разных форматов различимы.
- Порядок кадров сохраняется. Строки статуса и других событий не изображают дополнительные CAN-кадры.
- При доступной связи завершение содержит финальный статус устройства. Без связи CLI явно пишет локальное завершение и не выдумывает финальные счётчики.
- Полученная часть CSV читается после прерывания. Аварийное завершение процесса может оставить последнюю неполную строку; отсутствие штатного события завершения означает незавершённую сессию. Выход с экрана сохраняет уже полученное, но сохранность всех буферов после отключения питания/сбоя ОС не обещается.
- Точное кодирование UART, имена команд, синтаксис аргументов и нормализация диапазонов, имена CSV-колонок, форматы времени и типизированные значения выбираются при реализации в пределах этой семантики. До завершения реализации публикуется полный фактический контракт с единицами, ошибками и примерами реальных строк/CSV; вымышленные команды и альтернативные схемы недопустимы.

## Testing Decisions

### Согласованная граница проверок

- С пользователем согласовано: основная граница автоматизированных сценариев — **публичный CLI → документированный результат и событийный CSV**, плюс отдельная обязательная аппаратная приёмка. Не предписывать новые низкоуровневые тестовые API ради каждой задачи, очереди или callback.
- Проверять внешнее поведение, границы, переходы, ошибки и инварианты, а не структуру модулей, имена внутренних функций, размеры очередей, текст исходников или эхо mock-вызовов.
- На этой границе проверяются host CLI, UART-контракт с устройством и экспорт CSV. Управляемый serial-peer допустим для воспроизводимых потоков, ошибок и разрывов; он не доказывает работу прошивки, физического CAN или CH343. При наличии реального устройства те же внешние сценарии выполняются сквозным образом.
- OBD-профили, UI-навигация, сохранение после отключения питания и передача владения CAN проверяются через реальную плату и ECU/симулятор. Не добавлять CLI-команды для удалённого входа в Logger или `Apply` только ради удобства тестов.
- Готового набора аналогичных автоматизированных тестов в исследованных app/board/host-частях не найдено. Существующий полезный публичный контракт — снимок данных дашборда; он не заменяет проверку экранов и не является основанием вводить отдельный тестовый слой. При реализации повторно проверить доступные средства и использовать подходящие существующие seams, если они появились.
- Постоянные тесты должны ловить правдоподобные ошибки потребителя: неверное включение границы диапазона, смешение 11/29-bit, ложное подтверждение конфигурации, потерю признаков кадра, неверное завершение или вымышленные счётчики. Они должны быть детерминированными, изолированными и безопасными для полного набора.

### Проверяемые сценарии и критерии приёмки

| Область | Наблюдаемое доказательство |
|---|---|
| Сборка | `make build` проходит без новых предупреждений |
| Навигация и стиль | На плате работают `Errors msg` → настройки → Logger и возврат; назначение поля ошибок сохранено; главный экран не переработан |
| Черновик и Apply | Выбор без Apply не меняет CAN/сохранённый профиль; успешный Apply сбрасывает старые измерения/поддержку PID и запускает обнаружение; аппаратная ошибка видима; `No ECU` не вызывает откат |
| Все OBD-профили | Каждый из четырёх вариантов работает с соответствующим ECU/симулятором; 29-bit проверяется по фактической адресации запросов и ответов |
| Перезапуск | После отключения питания восстанавливается только сохранённый профиль дашборда; Logger не стартует |
| Владение и пассивность | При входе в Logger OBD прекращается; во время захвата отсутствуют собственные запросы, тестовые передачи и ACK; стенд учитывает отдельный ACK-узел |
| Запрет удалённого входа | Подключение/обнаружение/статус не меняют режим; старт вне Logger даёт машинную ошибку и не останавливает OBD |
| Явная конфигурация | Без обязательных параметров захват не начинается; недостижимая скорость отклоняется без округления/частичного применения; запрошенная и эффективная конфигурации различимы |
| Allowlist | Точный ID, обе включительные границы, объединение/пересечение диапазонов как «ИЛИ», пустой список и режимы `11`/`29`/`both`; неподходящие кадры отсутствуют в результате и не увеличивают потери |
| Признаки кадра | CSV различает одинаковые числовые ID двух форматов, RTR, DLC, нулевые байты/ведущие нули и время приёма устройства; порядок кадров сохранён |
| Таймер, Ctrl-C и повтор | Оба способа прекращают захват, закрывают CSV/освобождают порт, оставляют Logger открытым; следующий захват начинается только новой командой и может использовать другую конфигурацию |
| Выход касанием | Активный захват немедленно прекращается без подтверждения; доступный CLI получает `user_exit` и сохраняет полученную часть; дашборд возобновляет OBD с сохранённым профилем |
| Heartbeat и разрыв | При тихой шине heartbeat поддерживает сессию; 3 секунды без служебных сообщений прекращают захват; возвращение клиента не продолжает старую сессию |
| Подтверждения | Экран и статус отличают TX от получения CLI; подтверждённый номер не трактуется как fsync или отсутствие upstream-потерь |
| Перегрузка | Управляемая нагрузка демонстрирует drop-new и сохранение порядка; захват продолжается; программные отбрасывания и аппаратные переполнения отражаются раздельно с честной неизвестностью числа кадров |
| Протокольный поток | Асинхронные кадры не смешиваются с ответами команд; boot noise допускается только до сессии; ошибка активного потока не скрывается; неподдерживаемая версия/некорректная команда дают машинно-различимый результат |
| CSV и завершение | Обычный CSV-парсер читает все типы событий без sidecar; метаданные достаточны; подтверждённое, локальное и отсутствующее штатное завершение различимы; нет вымышленных итоговых счётчиков |
| Реальный UART | На CH343 проверены 2 Мбод, отсутствие смешивания с console/logging и возможность штатной прошивки; записаны условия нагрузки и наблюдаемые потери |
| CLI на ОС | На macOS и Linux проверены подключение, конфигурация, захват, завершение, машинные результаты и exit codes; непроверенная ОС явно отмечается |
| UI на плате | Проверены касания, читаемость конфигурации/фильтра, состояния подтверждённой передачи и потерь; сырые кадры на экран не выводятся; нет обновлений удалённых виджетов |

- Для аппаратной проверки использовать соответствующий ISO 15765-4 ECU/симулятор. Известный стендовый IMSB5010 отвечает на запросы, но не является источником автономных broadcast-кадров: тишина пассивного захвата этого устройства не доказывает неисправность логгера. Нужен подходящий источник CAN-трафика; пассивность/ACK подтверждаются средствами стенда, не только CSV.
- Сборка и serial-подмена не являются доказательством CAN, CH343 и touch. В отчёте реализации перечислить выполненные сценарии и фактические результаты; недоступные аппаратные критерии и платформы обозначить непроверенными, не выполненными.
- В рамках подготовки этой спецификации проверки будущей реализации не выполняются.

## Out of Scope

- Реализация прошивки или CLI в рамках публикации спецификации; для этого необходимо отдельное поручение.
- CAN FD, произвольная длина CAN-ID, изменение UART-параметров из CLI.
- Одновременный независимый логгер и OBD, автоматический подбор CAN-протокола/скорости, скрытые fallback-режимы.
- Сохранение профиля логгера, автозапуск/автовозобновление захвата, автоматические повторные захваты и восстановление кадров после разрыва.
- Запись на SD/во flash платы, сущности поездок, просмотр кадров или графиков на экране.
- Фильтры по payload, распознавание сигналов, встроенный LLM-анализ, выводы о неисправностях.
- Live-reconfiguration, несколько управляющих клиентов, daemon/IPC и параллельные команды к одному захвату.
- Windows, точная синхронизация часов, аппаратный flow control как предпосылка решения и гарантированно беспотерьная запись любой загрузки CAN.
- Переработка основного дашборда, расширение требований более широким планом проекта, новая универсальная тестовая/архитектурная платформа.

## Further Notes

- Источник согласованного объёма: [исходное ТЗ](../../docs/logger-settings-spec.md). Оно остаётся неизменным. Эта спецификация переводит его в формат локального трекера и добавляет согласованную границу проверок; не утверждает, что функции уже реализованы.
- [Текущий UI-дизайн](../../docs/design.md) задаёт оформление и существующие поля; [аппаратная справка](../../docs/hardware.md) — ограничения и стенд. Описания текущего display-only/11-bit поведения подлежат обновлению при реализации, а не ограничивают согласованную функцию. Более широкий план не является дополнительным критерием приёмки.
- По завершении реализации обновить UI-документацию, опубликовать фактические справки CLI/UART/CSV и сделать инструкции обнаружимыми из команд проекта. Не документировать предполагаемые команды как реализованные.
- Инструкция должна позволить следующему агенту: установить CLI; выбрать UART платы, а не USB симулятора; проверить совместимость, режим и возможности; попросить человека открыть Logger при необходимости; запустить ограниченный захват с явными скоростью/типом/фильтром; проверить конфигурацию, подтверждения, потери и завершение по результату/CSV; повторить эксперимент с другим фильтром; анализировать данные внешним LLM без вывода «нет кадров — нет сигналов»; попросить человека вернуться на дашборд касанием выхода.
- Точные имена команд, схема колонок и кодирование строк намеренно не выдуманы до реализации: свобода выбора синтаксиса не отменяет обязательной семантики и полного фактического контракта.
